# wiki-review

SCHEMA.md와 [실행 형식](references/workflow.md)이 공통 계약이다. 입력은 변경 초안·사용자 응답 또는 기존 위키 점검 요청이다. 전체 원천 조사는 update, 원천 기반 초안은 ingest, 답변과 파일링 초안은 query가 맡는다. 구조 검사는 `company-wiki lint`가 수행한다.

위치는 고정이다: 설정 ~/company-wiki/wiki.toml, 위키 ~/company-wiki/llm-wiki, 변경 절차 폴더 ~/company-wiki/workspace/wiki-changes. wiki.toml에서 원천·검토자를 확인하고, 위키의 SCHEMA.md를 기준으로 작업한다.

반영 경로는 `company-wiki review`의 **prepare → preview → update를 실행한 담당자의 세션 답변 → decide → apply → 위키 저장소 main에 커밋·푸시**다. PR·브랜치는 쓰지 않는다. 담당자가 자기 페이지를 직접 고친 경우는 lint → `company-wiki registry record <페이지>` → main 커밋·푸시로 반영된다. 검토 기록은 변경 절차 폴더에 두고 위키에 넣지 않는다.

## 출력 계약

검토 요청의 최종 출력은 **사람이 판단해야 할 핵심 질문의 번호 목록**이다. 조사·초안·검사·의미 검토는 질문을 뽑기 위한 내부 과정이며, 작업 보고서나 변경 내역 나열로 답변을 대신하지 않는다.

- 질문은 wiki update를 실행한 담당자에게 보낸다. 질문마다 대상 페이지를 밝힌다.
- 담당자가 근거로 답할 수 없는 조직 결정·다른 부서 영역은 질문 앞에 **[리더 확인 필요]**를 붙이고 누구(관련 부서 리더)에게 무엇을 확인할지 적는다. 리더의 답은 검토 근거이며 승인이 아니다.
- 한 항목에는 하나의 판단을 묻고, 필요한 현재/제안 내용과 적용 범위를 담아 1~2문장으로 쓴다. 같은 판단은 묶되 사실 확인과 반영 승인을 섞지 않는다.
- 선택지나 추천이 도움이 되면 질문 안에 짧게 넣는다. 승인뿐 아니라 수정·보류·제외도 선택할 수 있게 한다.
- 근거·해석·추천 이유·상세 diff는 검토 파일에 보존한다. 질문에는 판단에 꼭 필요한 맥락만 남기고, 필요하면 해당 검토 파일 링크를 붙인다. 승인 질문은 무엇을 어디까지 반영하는지 자체로 알 수 있어야 한다.
- 모든 질문을 한 번에 제시한다. 이미 결정됐거나 근거로 해결할 수 있는 사항, 내부 작업 절차는 묻지 않는다.
- 남은 판단이 없으면 질문을 만들지 않고 “판단이 필요한 질문이 없습니다.”라고만 답한다. 미해결 검사 오류나 근거 누락으로 검토가 막힌 경우에는 이를 숨기지 말고, 필요한 자료·범위 결정을 묻는 질문에 포함한다.

사용자 답변 이후 반영 요청을 처리할 때는 반영 결과를 짧게 알리고, 남은 판단이 있으면 같은 형식의 질문 목록으로 제시한다.

## 1. 검토 가능한 버전 준비

`company-wiki review status`로 기존 제안·승인을 확인한다. 같은 페이지를 바꾸는 주제는 묶고 기존 검증 이력을 보존한다. prepare로 전후·근거를 고정한 뒤 preview로 실제 합본을 검사한다. 오류를 해결하지 못한 항목은 반영하지 않고 원인과 미확인 범위를 보고한다.

preview와 apply는 lint를 자동 실행한다. 구조 오류는 원문·이동 경로를 확인해 초안에서 고치며, 대상을 임의 생성하거나 링크를 지워 검사만 통과시키지 않는다. 경고는 판단 신호다. 경고를 없애려고 인용 번호나 해시를 고치지 않는다. moved는 같은 내용이 새 줄에 있는지 확인한 뒤 번호를 고치고, changed는 원문을 다시 읽어 문장·관계를 재검토한다.

구조 검사를 통과한 합본에서 다음을 의미 검토한다. 상세 판단 기준은 SCHEMA.md를 따른다.

- 인용이 실제 주장을 지지하며, 한 사례·계획·제안이 일반 원칙·실행·성과로 확대되지 않았는가?
- 조직이 실제로 채택한 내용인가? 미해결 질문·연구 과정·외부 주장이 섞이지 않았는가?
- owner가 근거로 확인되는가? entities가 업무 데이터를 복제하지 않는가?
- 주장 차이가 동일 대상·시점·조건에서 충돌하는가, 시점·범위·명칭 차이인가?
- 기존 검증 이력과 관계의 방향·적용 범위, 사용자 제한 조건을 유지했는가?

기존 위키 점검 요청이면 먼저 `company-wiki lint`와 `company-wiki registry`를 실행하고, changed·moved·expired·missing 인용과 관계로 영향받는 페이지, 지정 범위 페이지의 근거를 대조한다. 발견한 문제를 수정 초안으로 만들어 실행한 담당자에게 판단 질문으로 올린다. SCHEMA 7절에 따라 점검 결과만으로 정식 페이지를 수정하거나 무효로 표시하지 않는다.

현재/제안 표현·근거·해석·추천 이유·적용 범위와 diff를 검토 파일에 준비한 뒤, 출력 계약에 따라 질문 목록을 만든다. 주제별 카드는 내부 버전 단위이며 질문을 순차 발송하라는 뜻이 아니다.

update에서 호출되면 질문 목록과 내부 검토 자료를 반환한다. 사용자에게 별도로 질문하거나 반영하지 않고, update가 전체 질문을 한 번에 제시한 뒤 사용자 결정에 따라 재개한다. 구조 오류 0은 의미 정확성이나 사람 승인을 보증하지 않는다.

## 2. 사람 결정 기록

실행한 담당자 본인의 실제 응답을 확인해 decide로 정확한 버전에 승인/수정/보류/제외를 기록한다. 사실·명칭·해석·관계·확정성·범위를 구분하고 단순 사실 확인을 전체 반영 승인으로 확대하지 않는다. 이미 승인된 항목과 명시적 수정 지시는 재질문하지 않는다. 수정 지시에 없는 새 해석이나 모호한 승인 범위만 확인한다. 담당자가 리더에게 확인한 내용은 그 답이 남은 등록 원천(세션·Slack 사본 등)을 근거로 인용하고, 승인은 담당자의 답으로만 기록한다.

## 3. 승인 범위 반영과 검증

apply 직전에 카드와 사용자 제한 조건을 대조하고 승인된 주제만 지정한다. 부분 승인으로 연결이 깨지면 필요한 의존 관계를 해결한다. 기준 문서가 바뀌면 해당 주제만 다시 준비한다. 중단 journal은 recover하되 다른 편집을 덮어쓰지 않는다.

apply의 구조 검사와 별도로 **인용이 주장을 지지하는가, 사용자 판단이 정확히 옮겨졌는가, 범위 밖 해석·연결이 들어갔는가**를 확인한다. 승인 근거 지원은 현재 Claude·Codex 사용자 메시지에 한정되며 다른 원천은 지원을 확인하기 전 우회 인용하지 않는다.

`company-wiki lint`와 status·applied.jsonl을 확인하고 apply가 쓴 페이지·index·.verification/registry.json만 위키 저장소 main에 커밋·푸시한다. 커밋 메시지는 apply가 출력한 "커밋 메시지:" 아래의 제목과 trailer(Wiki-Change·Wiki-Revision·Approved-By·Approval-Evidence)를 고치지 않고 쓴다. 사용자가 지정한 저장소와 공개 범위를 따른다. 반영 파일·검사 실패/미검증·남은 판단을 보고한다. 전체 조사 경계 갱신은 update의 inventory 계약을 따르며 apply 완료와 혼동하지 않는다.
